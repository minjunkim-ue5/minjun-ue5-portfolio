2~4인 온라인 협동 물리 운반 게임에서 **물리 · 아이템 파트**를 단독으로 맡아 구현한 C++ 코드입니다.

|---|---|
| 엔진 | Unreal Engine 5.4 (C++) |
| 네트워크 | Listen Server · 서버 권위 + 클라이언트 보간 |
| 기간 | 2026-08-06 ~ 2026-08-28 (작업일 12일) |
| 팀 | 6인 · 파트 분담 |
| 담당 | 물리 / 아이템 (단독) |
| 커밋 | 45개 |
| 기여 | `Source/` 기준 +10,844 / -3,129 줄 |

> 이 저장소는 **발췌본**입니다. 팀 저장소에서 제가 작성한 `.h` / `.cpp` 만 원본 바이트 그대로
> 옮겨 담았으며, 에셋 · 설정 · 다른 파트 코드는 포함하지 않아 단독 빌드되지 않습니다.

## 담당 범위

**맡은 것**
- 노획물 액터의 물리 특성 (질량, 콜리전, 복제)
- 잡기 / 놓기 / 던지기 상호작용 판정
- 충돌 · 낙하 감지와 그에 따른 시각 연출
- 노획물 고유 특성 3종 — 중량형 · 파손형 · 불안정형
- 노획물의 가치($) 계산, 대형 금고, 카트, 장비(점착 폭탄)

**맡지 않은 것** — 집기 입력 · 트레이스 (플레이어 파트) / 소음 시스템 (소음 파트) / 경비 AI (AI 파트) / 레벨 기믹 (환경 파트)

## 아키텍처 — 특성을 상속이 아닌 컴포넌트로

처음에는 `ALootHeavy`, `ALootFragile` 같은 자식 클래스로 설계했습니다.
"무겁고 잘 깨지는 궤짝"을 만들려는 순간 막혔습니다. 액터 계층에서 다중 상속은 선택지가 아닙니다.

특성을 **컴포넌트**로 옮겼습니다. 각 컴포넌트가 `BeginPlay` 에서 자기 태그를 스스로 답니다.

```cpp
// LootHeavyComponent.cpp:32
OwnerLoot->AddLootTypeTag(HHTags::Loot_Type_Heavy);
// LootDurabilityComponent.cpp:100
OwnerLoot->AddLootTypeTag(HHTags::Loot_Type_Fragile);
// LootStabilityComponent.cpp:93
OwnerLoot->AddLootTypeTag(HHTags::Loot_Type_Unstable);
```

**BP 에 컴포넌트를 붙이는 행위 자체가 특성 부여**가 되어, 조합이 자유로워졌습니다.
`Loot.Type.*` 태그 자체는 전 파트가 함께 쓰는 팀 공용 태그 파일에 등록합니다.

부수 효과로 "특성이 하나도 없는 평범한 노획물"도 가능해졌는데, 이때 태그가 비어 플레이어 파트의 집기 트레이스가 액터를 지나치는 문제가 생겼습니다. 안전망을 뒀습니다.

```cpp
// LootBase.cpp:308 — 특성이 없어도 부모 태그 하나는 달아야 집기 판정에 걸린다
if (LootTypeTags.IsEmpty())
{
    AddLootTypeTag(HHTags::Loot_Type);
}
```

수치는 코드 밖으로 뺐습니다 — `DT_LootCatalog` / `DT_LootDurability` / `DT_LootHeavy` /
`DT_LootStability` 네 개 표에 행 이름으로 조인하고, 표가 채우는 칸은 BP 디테일에서 잠갔습니다.
표와 인라인 값이 둘 다 편집 가능하면 어느 쪽이 적용됐는지 추적할 수 없기 때문입니다.

## 파트 경계 설계

6인이 한 저장소를 쓰는 만큼, 어디까지가 내 책임인지를 **문장으로 먼저 정의**하고 코드를 짰습니다.

### 1. 아이템은 값만 제공하고, 적용은 플레이어 파트가 한다

중량형을 들면 이동 속도가 30%로 떨어집니다. 이 배율을 제가 직접 `MaxWalkSpeed` 에 곱하면
두 가지 문제가 생깁니다 — 플레이어 파트도 같은 일을 하면 **배율이 두 번 곱해지고**(0.3 × 0.3),
`MaxWalkSpeed` 가 GAS 어트리뷰트라 다음 어트리뷰트 변화 때 값이 지워집니다.

```cpp
// Carryable.h:35 — [경계] 이동 속도를 여기서 깎지 않는다. 값만 알린다.
virtual float GetCarrySpeedMultiplier() const = 0;
```

### 2. 아이템은 물리적 사실만 알린다

`OnHit` 에서 "무엇이 / 얼마의 충격으로 / 무슨 재질에" 부딪혔는지만 `FLootImpactEvent` 로
방송합니다. 그게 몇 미터까지 들리고 경계도를 몇 % 올리는지는 판단하지 않습니다 —
소음 시스템과 `DT_NoiseProfiles` 의 몫입니다.

델리게이트를 **C++ 전용 멀티캐스트**로 둔 것도 같은 이유입니다. BP 에 노출하면 누군가
블루프린트에 소음 판정 로직을 짜기 시작하고, BP 는 diff 도 병합도 되지 않습니다.

## 트러블슈팅

### 1. 물리 낙하 1회에 `OnHit` 이 5~15회 발생한다

튕김 · 구름 · 미세 접촉이 전부 개별 이벤트로 옵니다. 그대로 방송하면 상자 하나를
떨어뜨렸을 때 파손형이 3회 누적으로 즉사하고, 소음 파트의 경계도가 즉시 100%가 됩니다.

두 겹으로 게이팅했습니다 — **임펄스 임계값 미만 무시**, **같은 대상 0.3초 내 재발행 차단**
(`ImpactDebounceSeconds = 0.3f`).

임계값을 감으로 정하지 않기 위해 **디버그 출력을 먼저 만들었습니다.** 기각된 충돌까지
화면에 찍고, 원시 히트 수(`DebugRawHitCount`)와 확정 수(`DebugConfirmedCount`)의 비율을
눈으로 확인한 뒤 값을 정했습니다. 관측 수단 없이 튜닝하면 그 숫자를 계속 의심하게 됩니다.

### 2. 리슨 서버의 호스트 창은 정상으로 보인다

클라이언트에서 노획물을 들 수 없는 현상을 발견했습니다. 호스트 창에서는 3주 내내
정상 동작하던 기능입니다.

원인은 GAS 어빌리티의 `NetExecutionPolicy` 였습니다. 엔진 기본값이 `LocalOnly` 인데
어빌리티 내부는 `ActorInfo->IsNetAuthority()` 로 게이트를 걸고 있어, 클라이언트에서는
그 블록에 영원히 도달하지 않습니다. 그런데 **리슨 서버의 호스트는 로컬 플레이어가 곧 서버**라
`LocalOnly` 로 실행돼도 권한 검사를 통과합니다. 그래서 호스트에서만 멀쩡했습니다.

해당 코드는 플레이어 파트 소관이라 직접 수정하지 않았습니다. 대신 원인과 재현 경로
(클라이언트 창 / 대상 어빌리티 3종 / 근거가 된 대조 사례)를 정리해 담당자에게 전달했습니다.

이후 멀티 기능은 **처음부터 클라이언트 창에서** 확인하는 것을 원칙으로 삼았습니다.
Number of Players 2 이상 / Run Under One Process 해제 / Play As Listen Server.

### 3. 놓는 순간 물건이 캐릭터 캡슐과 겹친다

소지 중에는 물리를 끄고 손 소켓에 Attach 하는데, 놓는 순간 물리를 켜면 물건이 캡슐 안에
박혀 있어 겹침 해소 힘 때문에 궤도가 흐트러집니다.

조사에서 두 가지를 확인했습니다.

- **캐릭터 스켈레탈 메시는 물리 접촉을 만들지 않는다** — 콜리전 프로파일이 Query Only입니다.
  "손이 물체를 감싸서" 라는 초기 가설은 틀렸고, 원인은 캡슐 하나였습니다.
- **`IgnoreActorWhenMoving` 은 스윕 전용** — 시뮬레이션 중인 물리 바디에는 효과가 없습니다.

현재는 물리를 켜기 전에 스윕으로 안전 거리를 재고, 실패하면 MTD(`ComputePenetration`)로
빼내는 방식입니다. 개선안을 4가지 설계했지만 **적용하지 않기로 결정했습니다.**

곧 들어올 팔 뻗기 애니메이션이 물건을 캡슐 밖에 위치시켜 원인 자체를 없애기 때문입니다.
지금 우회로를 넣으면 애니메이션이 들어온 뒤 지워야 할 코드가 됩니다. 대신 조사 결과와
판단 근거를 기록으로 남겨 두었습니다.

### 4. 설계를 두 번 폐기했다

**`PhysicsHandle` 로 물건을 드는 방식** — 물리를 켠 채 끌면 물리감은 좋지만, 클라이언트마다
시뮬레이션 결과가 미세하게 달라 사람마다 물건 위치가 어긋납니다. **물리 OFF + 소켓 Attach**로
전환하고, 물리감은 소지 중 스윕 트레이스로 벽 접촉을 감지해 보완했습니다.

**`PhysicsConstraint` 로 2인 협력 캐리** — 물리 제약을 두 플레이어에게 거는 방식은
네트워크에서 깨집니다. 대신 **두 그립 사이 거리 제약 하나를 위치 보정으로** 풀었습니다.

이 설계에서 예상하지 못한 결과가 나왔습니다. 한 명이 멈추면 다른 한 명은 그 사람을 중심으로
원형으로 돌 수밖에 없는데, 이 "서로 방해되는" 감각이 협동의 핵심 재미였습니다.
따로 구현한 동작이 아니라 **제약 하나에서 저절로 나온 결과**입니다.

단, 서버가 매 프레임 폰 위치를 강제하면 `CharacterMovementComponent` 의 클라이언트 예측과
충돌해 캐릭터가 떨립니다(호스트에서는 보이지 않습니다). 그래서 제약은 이동 예측 경로 안에서
적용되어야 하고, 저는 **그립 지점 · 거리 · 제약을 푸는 함수까지만** 제공했습니다.
