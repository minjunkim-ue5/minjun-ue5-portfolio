## 담당 범위

**맡은 것**
- 노획물 액터의 물리 특성 (질량, 콜리전, 복제)
- 잡기 / 놓기 / 던지기 상호작용 판정
- 충돌 · 낙하 감지와 그에 따른 시각 연출
- 노획물 고유 특성 3종 — 중량형 · 파손형 · 불안정형
- 노획물의 가치($) 계산, 대형 금고, 운반용 카트
- **던져 쓰는 장비 5종과 그 공통 베이스** — 점착 폭탄 · 미끼 · 응급 키트 · 정찰 드론 · EMP
- **사람에게 붙는 패시브** — 고무창 신발 (액터가 아닌 컴포넌트)
- **은신처 상점** — 진열대, 가격표, 팀 공용 골드 지출 판정

**맡지 않은 것** — 집기 입력 · 트레이스 (플레이어 파트) / 소음 시스템 (소음 파트) / 경비 AI (AI 파트) / 레벨 기믹 · 감시 카메라 (환경 파트) / 상점 UI (UI 파트)

## 아키텍처 — 특성을 상속이 아닌 컴포넌트로

처음에는 `ALootHeavy`, `ALootFragile` 같은 자식 클래스로 설계했습니다.
"무겁고 잘 깨지는 궤짝"을 만들려는 순간 막혔습니다. 액터 계층에서 다중 상속은 선택지가 아닙니다.

특성을 **컴포넌트**로 옮겼습니다. 각 컴포넌트가 `BeginPlay` 에서 자기 태그를 스스로 답니다.

```cpp
// LootHeavyComponent.cpp:32
OwnerLoot->AddLootTypeTag(HHTags::Loot_Type_Heavy);
// LootDurabilityComponent.cpp:101
OwnerLoot->AddLootTypeTag(HHTags::Loot_Type_Fragile);
// LootStabilityComponent.cpp:94
OwnerLoot->AddLootTypeTag(HHTags::Loot_Type_Unstable);
```

**BP 에 컴포넌트를 붙이는 행위 자체가 특성 부여**가 되어, 조합이 자유로워졌습니다.
`Loot.Type.*` 태그 자체는 전 파트가 함께 쓰는 팀 공용 태그 파일에 등록합니다.

부수 효과로 "특성이 하나도 없는 평범한 노획물"도 가능해졌는데, 이때 태그가 비어 플레이어 파트의 집기 트레이스가 액터를 지나치는 문제가 생겼습니다. 안전망을 뒀습니다.

```cpp
// LootBase.cpp:321 — 특성이 없어도 부모 태그 하나는 달아야 집기 판정에 걸린다
if (LootTypeTags.IsEmpty())
{
    AddLootTypeTag(HHTags::Loot_Type);
}
```

### 장비는 상태 기계 하나를 공유한다

장비도 같은 방침입니다. `AEquipmentBase` 가 상태 기계를
(`Idle → Carried → InFlight → Deployed → Active → Spent`) 전부 갖고, 각 장비는 생성자에서
값을 정하고 달라지는 지점만 덮어씁니다. **미끼(`ADecoy`)는 함수가 하나도 없습니다** —
생성자뿐이고, 그래도 던지면 날아가 떨어진 자리에서 20초간 소리를 냅니다.

| 장비 | 베이스에 더한 것 |
|---|---|
| 미끼 | 없음 (값만) |
| EMP | `OnActivated` — 반경 안의 감시 카메라에 정지를 알린다 |
| 점착 폭탄 | `OnActivated` — 반경 안의 금고 문에 폭파를 알린다 |
| 응급 키트 | `OnDeployed` / `OnActivated` — 맞은 사람 또는 반경 안의 다운된 동료를 일으킨다 |
| 정찰 드론 | 비행 · 시점 인수 · 입력 (베이스 밖의 고유 기능) |
| 고무창 신발 | 액터가 아니다 — 사람에게 붙는 `UActorComponent` |

## 데이터 — 수치 하나가 두 곳에 있으면 조용히 어긋난다

수치는 코드와 BP 밖으로 뺐습니다. 원본은 저장소 루트의 CSV 이고(`Data/*.csv`), 그것을
`DT_*` 로 임포트해 씁니다. CSV 로 둔 이유는 **`.uasset` 은 병합이 안 되기 때문**입니다 —
표를 에디터에서만 고치면 두 사람이 다른 행을 고쳐도 한쪽 작업이 사라집니다.

| 표 | 정하는 것 |
|---|---|
| `LootCatalog.csv` | 노획물의 가치 · 무게 등급 · 메시 |
| `LootDurability.csv` | 파손형 — 파괴 임계 횟수, 회당 가치 손실 |
| `LootHeavy.csv` | 중량형 — 1인/2인 속도 배율, 그립 간 거리 |
| `LootStability.csv` | 불안정형 — 유출 각도, 그레이스 시간, 안전 속도 |
| `ShopCatalog.csv` | 구매 장비 7종의 판매가 |

**행 이름을 태그 이름 그대로 씁니다.** `Equipment.Drone` 행을 `Equipment.Drone` 태그로
바로 찾습니다(`ShopSettings.h:69`). 그래서 행 구조체에 `ItemTag` 열이 없습니다 —
넣으면 같은 값이 두 벌이 되고, 행 이름만 고쳤을 때 조용히 어긋납니다(`ShopTypes.h:11-19`).

같은 원칙을 연출에도 적용했습니다. EMP 의 펄스 구를 나이아가라에 크기로 박아 두면,
나중에 `PulseRadius` 를 바꿨을 때 **보이는 구와 실제로 꺼지는 범위가 어긋납니다.** 그러면
"분명 닿았는데 안 꺼진다"로 나타나고 원인을 찾기 어렵습니다. 그래서 베이스에 훅을 하나 두고
(`EquipmentBase.h:452`), 게임 수치를 나이아가라 User 파라미터로 넘깁니다.

```cpp
// EMPDevice.cpp:47 — 이펙트는 이 값을 받아 구의 반지름으로 쓰기만 한다
Effect->SetFloatParameter(TEXT("Radius"), PulseRadius);
```

## 파트 경계 설계

6인이 한 저장소를 쓰는 만큼, 어디까지가 내 책임인지를 **문장으로 먼저 정의**하고 코드를 짰습니다.

### 1. 아이템은 값만 제공하고, 적용은 플레이어 파트가 한다

중량형을 들면 이동 속도가 30%로 떨어집니다. 이 배율을 제가 직접 `MaxWalkSpeed` 에 곱하면
두 가지 문제가 생깁니다 — 플레이어 파트도 같은 일을 하면 **배율이 두 번 곱해지고**(0.3 × 0.3),
`MaxWalkSpeed` 가 GAS 어트리뷰트라 다음 어트리뷰트 변화 때 값이 지워집니다.

```cpp
// Carryable.h:41 — [경계] 이동 속도를 여기서 깎지 않는다. 값만 알린다.
virtual float GetCarrySpeedMultiplier() const = 0;
```

### 2. 아이템은 물리적 사실만 알린다

`OnHit` 에서 "무엇이 / 얼마의 충격으로 / 무슨 재질에" 부딪혔는지만 `FLootImpactEvent` 로
방송합니다. 그게 몇 미터까지 들리고 경계도를 몇 % 올리는지는 판단하지 않습니다 —
소음 시스템과 `DT_NoiseProfiles` 의 몫입니다.

델리게이트를 **C++ 전용 멀티캐스트**로 둔 것도 같은 이유입니다. BP 에 노출하면 누군가
블루프린트에 소음 판정 로직을 짜기 시작하고, BP 는 diff 도 병합도 되지 않습니다.

### 3. 다른 파트에 요청하기 전에 그쪽 public API 를 먼저 읽는다

장비를 만들며 두 번, "이건 저쪽 파트에 요청해야 한다"고 판단했는데 두 번 다 이미
만들어져 있었습니다.

- **응급 키트의 부활** — 대상의 GE 클래스를 알아야 할 것 같았지만, 플레이어 파트가 이미
  태그로 지우는 경로를 만들어 두었습니다. 한 줄로 끝났습니다(`MedKit.cpp:114`).
- **고무창 신발의 소음 감쇄** — 소음 파트의 `FNoiseModifier::Multiplier` 주석에
  **"고무창 신발 0.5"** 가 처음부터 적혀 있었습니다. 등록·해제만 하면 됐습니다.

그래서 **드론도 플레이어 파트를 한 줄도 고치지 않고** 만들었습니다(트러블슈팅 11번).
이 프로젝트는 문서가 코드보다 자주 뒤처져서, 문서를 믿고 요청서를 쓰면 이미 있는 것을
다시 만들게 됩니다.

## 트러블슈팅

### 1. 물리 낙하 1회에 `OnHit` 이 5~15회 발생한다

튕김 · 구름 · 미세 접촉이 전부 개별 이벤트로 옵니다. 그대로 방송하면 상자 하나를
떨어뜨렸을 때 파손형이 3회 누적으로 즉사하고, 소음 파트의 경계도가 즉시 100%가 됩니다.

두 겹으로 게이팅했습니다 — **임펄스 임계값 미만 무시**, **같은 대상 0.3초 내 재발행 차단**
(`ImpactDebounceSeconds = 0.3f`).

임계값을 감으로 정하지 않기 위해 **디버그 출력을 먼저 만들었습니다.** 기각된 충돌까지
화면에 찍고, 원시 히트 수(`DebugRawHitCount`)와 확정 수(`DebugConfirmedCount`)의 비율을
눈으로 확인한 뒤 값을 정했습니다. 10kg 기준 100cm 낙하 임펄스 5031 / 150cm 6497 / 300cm 9622,
착지 후 튕김은 500~900 대로 나와, 그 사이를 가르는 3000을 임계값으로 잡았습니다.
관측 수단 없이 튜닝하면 그 숫자를 계속 의심하게 됩니다.

### 2. 서버와 클라이언트가 같은 함수를 부르게 만들었다

부착 · 물리 토글 · 콜리전 프로파일 변경은 복제되지 않는 로컬 호출입니다. 서버에서만
실행하면 클라이언트 화면에서는 물건이 손에 안 붙습니다.

복제되는 값은 "누가 들고 있는가" 하나뿐으로 좁히고, 서버 호출과 `OnRep` 이 같은 함수
하나를 공유하게 만들었습니다.

```cpp
// LootBase.cpp:945 — 클라이언트 쪽은 이 한 줄이 전부다
void ALootBase::OnRep_PrimaryCarrier()
{
    ApplyCarryState();
}
```

`ApplyCarryState` 내부에서는 **물리 끄기 → 콜리전 프로파일 변경 → 어태치** 순서를
반드시 지켜야 합니다(`LootBase.cpp:1075-1076` → `:1184`). 런타임 중인 시뮬레이션 컴포넌트는
웰드 없이 부착할 수 없기 때문입니다. 이 패턴은 이후 팀 코딩 규약 문서에 프로젝트 표준으로
채택됐습니다.

### 3. 놓는 순간 물건이 캐릭터 캡슐과 겹친다

소지 중에는 물리를 끄고 손 소켓에 Attach 하는데, 놓는 순간 물리를 켜면 물건이 캡슐 안에
박혀 있어 겹침 해소 힘 때문에 궤도가 흐트러집니다.

조사에서 두 가지 막다른 길을 확인했습니다.

- **`IgnoreActorWhenMoving` 은 스윕 전용** — 시뮬레이션 중인 물리 바디 접촉에는 효과가 없습니다.
- **MTD(`ComputePenetration`) 단독 사용도 불완전** — 두 형상의 중심이 겹치면 밀어낼 방향이
  0벡터로 나옵니다(`LootBase.cpp:1235`).

최종 해결은 세 단계입니다.

1. 물리를 켜기 **전에** 스윕으로 안전 거리를 확보하고, 그래도 겹쳐 있으면 MTD로 한 번 더
   밀어냅니다(`LootBase.cpp:1274`).
2. 전용 콜리전 프로파일 `ReleasedLoot` (`LootBase.cpp:44`)을 만들어, 물리를 켜는 **첫
   프레임부터** 적용합니다(`:1110-1112`) — 프로파일을 나중에 바꾸면 이미 겹친 그 프레임에
   문제가 나서 늦습니다.
3. 이 프로파일은 사람 채널만 0.3초 동안 Ignore 하고(`ReleaseIgnorePawnSeconds`), 시간이
   지나면 원래 프로파일로 되돌립니다.

같은 수정으로, 점착폭탄이 던진 사람에게 붙어버리던 버그도 함께 사라졌습니다.

### 4. 파손형 노획물의 회당 가치 감소 설계

파손 1회마다 **현재 가치**의 30%를 복리로 차감합니다 (1000 → 700 → 490,
`LootDurabilityComponent.cpp:179-182`). 파괴되는 마지막 충격만 `Break` 가 100% 손실로
별도 처리합니다(`:184-187`).

원가 기준으로 정액 차감했다면, 파괴 임계치를 4~5회로 올린 물건은 파괴 전에 가치가 0에
닿아 마지막 충격들이 "공짜"가 되는 문제가 있었습니다. 파괴 충격까지 비율로 처리하면 같은
프레임에 `OnValueChanged` 가 두 번 발생해 HUD 가 깜빡이는 문제도 있어, 파괴는 별도
경로로 분리했습니다.

### 5. 불안정형 — 충돌이 아니라 틱으로 판정한다

파손형은 충돌 콜백("사건")으로 판정하지만, 불안정형은 "지금 기울어져 있는가"라는
"상태"라 매 틱 확인합니다(`LootStabilityComponent.cpp:104`).

소지 중에는 물리 회전을 그대로 읽지 않습니다. 물리가 꺼진 채 손 소켓에 붙어 있어서, 그대로
읽으면 기울기가 애니메이션이 손을 어디 두느냐로 정해져 플레이어가 통제할 수 없기
때문입니다. 대신 이동 속도가 안전 속도를 넘는 만큼, 넘긴 시간만큼 기울기를 직접
누적시킵니다(`:147-151`). 천천히 가거나 멈추면 다시 섭니다 — 멈춰서 숨 고르는 선택지가
있어야 합니다.

놓인 상태에서는 실제 물리 회전을 읽고, 그레이스 타임(0.5초, `TiltGraceSeconds`) 이상
지속되면 유출로 판정합니다(`:188`) — 던지면서 회전하는 것과 실제로 넘어진 것을 구분하기
위한 값입니다. 두 모드는 이어져 있습니다: 위태롭게 들고 오다 급히 내려놓으면 그 자세가
그대로 물리 회전이 되어 그 자리에서 샙니다(`:126-136`).

이동 속도는 강제로 깎지 않습니다. 얼마나 빨리 옮길지는 플레이어가 정하고, 그 대가를
물건이 치릅니다.

### 6. 중량형 — 두 번의 설계 폐기 끝에 "값만 제공"으로 정리했다

**`PhysicsHandle` 로 물건을 드는 방식** — 물리를 켠 채 끌면 물리감은 좋지만, 클라이언트마다
시뮬레이션 결과가 미세하게 달라 사람마다 물건 위치가 어긋납니다. **물리 OFF + 소켓 Attach**로
전환하고, 물리감은 소지 중 스윕 트레이스로 벽 접촉을 감지해 보완했습니다.

**`PhysicsConstraint` 로 2인 협력 캐리** — 물리 제약을 두 플레이어에게 거는 방식은
네트워크에서 깨집니다.

두 번 다 폐기하고 나서 내린 결론은, 중량형 컴포넌트가 직접 위치를 계산하지 않는
것이었습니다. 2인 캐리가 생기며 두 번째 운반자를 기억하고 그립 지점을 제공하는 고유
행동이 생겨 값(무게 등급)에서 컴포넌트로 승격은 했지만(`LootHeavyComponent.h:44-48`),
실제 위치 계산은 캐릭터 이동 예측을 쥔 플레이어 파트가 맡습니다. 서버가 매 프레임 폰
위치를 대신 정하면 `CharacterMovementComponent` 의 클라이언트 예측과 충돌해 캐릭터가
떨리기 때문입니다(호스트에서는 보이지 않아 발견이 늦었습니다). 그래서 이 컴포넌트는
**그립 소켓 이름과 그립 사이 거리까지만** 답하고, 두 사람이 그 지점을 향해 손을 붙이는
계산 자체는 플레이어 파트의 몫으로 넘겼습니다.

### 7. 운반용 카트 — 담기는 순간 소음과 파손을 함께 차단한다

카트에 물건을 실으면 하중이 바퀴를 통해 바닥에 전달되며 강한 수직 충격이 발생하고, 물리를
켜 둔 채 싣기 때문에 물건이 카트 바닥·턱·다른 물건과 계속 부딪힙니다. 조용히 옮기려고 산
장비가 실을 때마다 소리를 내고, 파손형은 밴까지 가는 동안 확실히 깨지는 문제가 있었습니다.

충돌 속도로 거르는 방법을 먼저 시도했지만, 카트에 물건을 담은 채로 이동하면 계속
충돌·파손이 발생할 수밖에 없어 실패했습니다.

해결은 "카트에 실려 있는 동안"이라는 상태 하나로 두 가지를 한 번에 막는 것이었습니다.

- 카트에 실리는 순간(`SetContainingCart`, `LootBase.cpp:718`) 노이즈 이미터에 배율 0
  감쇄를 걸어 소리를 원천 차단합니다.
- 충돌 판정 함수 맨 앞에서 "카트 적재 중이면 충격 자체를 보고하지 않는다"로 되돌려
  (`LootBase.cpp:1445-1453`) 파손 판정도 함께 막습니다.

카트 밖으로 나오면 그 즉시 다시 정상으로 돌아옵니다. 단, 불안정형(유출)은 기울기로
판정하지 충격으로 판정하지 않아서 이 경로를 타지 않습니다 — 카트 안에서도 계속 샙니다.
파손형은 카트 안에서 안전하고 불안정형은 그렇지 않은 것은, 노획물마다 카트와의 관계를
다르게 설계했기 때문입니다.

### 8. 호스트에서 던지면 보이고, 클라이언트에서 던지면 안 보였다

EMP 가 터질 때의 펄스 이펙트가 **호스트 창에서만** 나타났습니다. 로그를 양쪽에 찍어
비교한 결과 원인이 두 개였고, 둘 다 "호스트는 지연이 0" 이라는 사실에 가려져 있었습니다.

**① 자기를 파괴하는 액터의 연출을 복제 상태에 맡길 수 없다.**
원래는 상태가 `Spent` 로 복제되면 각 머신이 그것을 보고 이펙트를 띄웠습니다. 그런데 이
장비는 `Spent` 가 된 뒤 잠시 후 자기를 파괴합니다 — 그 사이에 상태가 못 나가면 클라이언트는
연출을 **영영** 못 봅니다. 당시 복제가 1.8초씩 밀리고 있어서 그대로 드러났습니다.

연출을 Multicast 로 직접 내려보내고, **위치를 인자로 실었습니다.** 클라이언트의 액터 위치가
서버보다 4.75m 뒤처져 있어서, 각자 자기 위치에 띄우면 엉뚱한 자리에서 터집니다.

```cpp
// EquipmentBase.h:436 — 위치는 서버 값이다. Reliable 인 것은 장비당 한 번만 나가기 때문
UFUNCTION(NetMulticast, Reliable)
void Multicast_SpentEffect(FVector_NetQuantize Location);
```

**② 그 4.75m 자체가 별개의 버그였다.** `ALootBase` 와 `AHandCart` 는
`SetPhysicsReplicationMode(PredictiveInterpolation)` 를 부르는데 **장비만 빠져 있었습니다.**
던질 때 물리는 모든 머신에서 켜지지만 발사 임펄스는 서버에서만 돕니다 — 클라이언트 사본은
추진력 없이 제자리에 떨어지고, 보정이 없으니 그대로 남습니다. UE 5.4 에는 전역 ini 키가
없어서 물리 액터마다 직접 불러야 합니다(`EquipmentBase.cpp:85`).

고친 뒤 재측정: 지연 1.78초 → 2ms, 위치 차이 4.75m → 9mm.

> 1.8초 지연의 근본 원인은 다른 파트에 있었습니다(경비 BP 가 시야 콘 메시를 복제해
> 번치가 넘치고 있었습니다). 측정값과 재현 경로를 정리해 전달했고 담당자가 수정했습니다.
> 다만 **그것이 고쳐졌어도 ①과 ②는 여전히 버그입니다** — 지연이 줄어 증상만 가려질
> 뿐이라, 양쪽을 따로 고쳤습니다.

### 9. 가격표를 못 읽으면 진열대가 팔지 않는다

진열대 가격을 BP 6개에 손으로 넣고 있었습니다. 정가는 태그 설정 파일의 주석에 적혀 있었지만
주석이라 코드가 읽지 못했습니다. `ShopCatalog.csv` 로 옮기면서 **표를 못 읽었을 때 어떻게
할지**가 문제가 됐습니다.

처음에는 BP 값으로 폴백했는데, 그쪽이 더 위험했습니다.

- 표 연결이 끊기면 **옛 가격으로 조용히** 팔립니다.
- BP 값을 0 으로 비워 두면 **공짜로** 팔립니다.
- 둘 다 플레이 중에는 드러나지 않고 밸런스만 어긋납니다.

안 파는 쪽으로 바꿨습니다. "지금은 살 수 없다"는 바로 눈에 띄고, 서버 로그가 어느 행이
없는지 알려줍니다. 가격은 `Data/ShopCatalog.csv` 하나가 정한다는 규칙도 분명해집니다
(`ShopDisplay.cpp:106-110`, `ShopDisplay.h:214-223`).

이때 가격 조회를 **모든 머신에서** 돌려야 했습니다. 구매 실패 문구가 가격을 읽기 때문에,
서버만 갱신하면 "잔액 부족" 문구의 금액이 클라이언트 창에서만 BP 값으로 뜹니다. 표는 모든
머신에 같은 에셋으로 있으니 복제할 필요가 없고, 각자 자기 것을 읽으면 됩니다.

### 10. 레벨에 배치된 액터는 Client RPC 를 부를 수 없다

구매 결과를 **구매자 본인에게만** 알려야 하는데, Client RPC 는 액터의 Owner 커넥션으로
갑니다. 레벨에 배치된 진열대는 Owner 가 없어서 호출이 아무 데도 가지 않고 경고만 남습니다.
`SetOwner(상호작용자)` 로 넘기는 방법은 두 명이 동시에 쓰면 엉킵니다.

엔진이 이미 통로를 갖고 있었습니다 — `APlayerController::ClientMessage`
(`ShopDisplay.cpp:255-261`). 그래서 결과를 세 갈래로 나눴습니다.

| 무엇 | 어디로 | 왜 |
|---|---|---|
| 자세한 사유 (설정 오류 등) | 서버 로그 | 개발자용. 회선에 실을 이유가 없다 |
| 결과 | 구매자의 PlayerController (Reliable) | 본인만 알아야 한다 |
| 소리 · 화면 표시 | 전원 (Unreliable) | 좁은 은신처에서 팀 공용 지갑을 쓰므로 서로 아는 게 맞다 |

결과를 문자열이 아니라 열거형으로 보낸 것도 같은 이유입니다. 문자열을 실으면 매 시도마다
그만큼이 회선을 타고, 나중에 UI 가 붙을 때 문구를 UI 쪽에서 정할 수 없습니다.

### 11. 정찰 드론 — 폰을 Possess 하지 않고 시점만 가져간다

드론을 조종하려면 보통 폰을 갈아치우지만, 그러면 조종사의 GAS · 다운 상태 · 소지품이 전부
걸립니다. 시점과 입력만 옮기는 방식으로 갔습니다.

```
PC->SetViewTarget(this, Blend)             시점
Subsystem->AddMappingContext(IMC, 100)     입력 — 우선순위가 높으면 같은 키를 드론이 가져간다
```

입력 우선순위를 플레이어보다 높게 두니 **"조종 중에는 몸이 멈춘다"를 따로 구현할 필요가
없어졌습니다.** 같은 키가 드론 쪽으로 소비되기 때문입니다. 결과적으로 플레이어 파트를
한 줄도 고치지 않았습니다. 조종 중 본인 몸은 던진 자리에 무방비로 서 있는데, 그것이 이
아이템의 대가입니다.

**카메라는 액터가 아니라 컴포넌트를 돌립니다.** 베이스가 `SetReplicateMovement(true)` 라
액터 회전을 로컬로 돌리면 복제된 회전이 매 프레임 그것을 덮어써서 시야가 떱니다. 요는
액터에, 피치는 카메라에 줍니다 — 요를 액터에 주지 않으면 조종사가 옆을 봐도 드론 몸통이
던져진 방향을 보고 있어 화면을 가로막고, 피치까지 액터에 주면 충돌 판정 기준이 기울어
벽에 박을 때 위아래로 튑니다.

**끝나는 길을 셋 두었습니다** — 시간 만료 / 준비 페이즈 종료 / `EndPlay`. 하나라도 놓치면
화면이 드론에 갇히기 때문에, 비행 종료 함수는 여러 번 불려도 안전하게 만들었습니다
(`Drone.h:47-52`).

조종사가 클라이언트일 때만 W 가 위로 가는 버그가 있었습니다. 베이스의 `OnActivated` 는
서버에서만 돌아서, 상태를 따로 복제하지 않으면 호스트만 드론을 조종할 수 있다는 것과
같은 뿌리였습니다. 원인과 해결은 `Drone.h:273-282` 주석에 남겼고,
RPC 가 각도를 변형하는 문제는 [TIL 로 따로 정리](TIL/2026-09-11-rpc-frotator-compression.md)했습니다.

### 12. 진입점이 3곳이라 스폰 구역도 3개여야 했다

저택에 들어가는 입구가 3곳이고, 플레이어가 그중 하나를 고릅니다. 산 장비를 실체화하는
스폰 구역이 하나뿐이면 다른 입구로 들어간 사람은 장비를 가지러 맵을 가로질러야 합니다.

구역을 진입점마다 두고, 각 구역이 "이번 판의 진입점이 내 것인가"를 스스로 판단하게 했습니다.
구역 하나가 확정된 진입점을 찾아가는 방식보다 이쪽이 낫습니다 — 진입점 바로 앞이 벽이나
계단인 경우를 코드가 알 방법이 없어서, 장비를 쌓아 둘 자리는 사람이 정해야 합니다.

판단에서 중요한 것은 **게임모드의 폴백과 결론을 맞추는 것**이었습니다. 고른 진입점이 이
레벨에 없으면 게임모드는 기본 진입점으로 떨어뜨립니다. 구역이 '고른 값'만 보면 플레이어는
1번 입구에서 시작했는데 장비는 아무 데도 안 나오는 상태가 됩니다(`EquipmentSpawnZone.cpp:106`).

```
1  고른 진입점 == 내 담당 태그                      → 내가 스폰한다
2  고른 진입점이 이 레벨에 있다 (내 것은 아니다)      → 그 구역이 맡는다
3  폴백: 내가 기본/첫 번째 진입점이면 내가 스폰한다 + 경고
```

태그가 비어 있으면 진입점과 무관하게 항상 스폰합니다. 진입점이 없는 레벨과, 구역을 하나만
두던 기존 배치가 그대로 동작해야 하기 때문입니다.
